Quisac · System Flow

How a repository becomes a live graph

Every request — a user clicking “index” or GitHub firing a push — becomes a durable row in Postgres, not an in-process goroutine. A pool of workers drains that queue, and only there does the graph work happen. This traces the whole path, from boot to Neo4j.

00

The cast

Nine moving parts across five layers. The colored spine on each card marks its layer; those same colors tag every node in the traces below, so you can see which layer a call crosses at a glance.

Browser
html/ · React + Vite
The dashboard. Starts the connect flow, POSTs an index request, then polls for the graph.
GitHub
external
OAuth provider, App API (tarballs & file contents), and the source of push webhooks.
Server
internal/server
HTTP transport only: routing, OAuth, webhook signature check, enqueue, poll. No graph logic.
Postgres
internal/db
Users, sessions, and the jobs table — the durable queue that everything hinges on.
Worker Pool
internal/worker
N workers + a maintenance loop. Claims jobs, runs them through ingest, records the outcome, reaps the dead.
Indexer
internal/ingest
The domain core. FullIndex and ProcessPush. Depends only on two interfaces it declares itself.
RepoSource
iface ← internal/github
Fetches repo contents: DownloadRepo, GetFileContent, HeadSHA. Satisfied by the GitHub App client.
GraphStore
iface ← internal/graphstore
Persists the graph in Neo4j: whole-repo saves and surgical per-file writes. Satisfied by the Cypher store.
Parsers
filewalk · resolver · treesitter
Turn a repo (or one file) into a core.Graph: tree-sitter parse, symbol/edge extraction, import resolution.
The seam that matters: ingest never imports github or graphstore. It declares RepoSource and GraphStore as interfaces, and cmd/quisac/main.go injects the real implementations. Dependencies point inward — that is why the worker, not the server, and the fakes, not Neo4j, can drive it in tests.
01

Boot — wiring the composition root

cmd/quisac/main.go --serve is the single place everything is constructed. Nothing news-up its own dependencies; they flow in from here.

  1. config.LoadenvConfig

    Read env into a typed config; fail fast if anything required is missing.

  2. db.OpenMigratePostgres

    Open the pool, then apply migrations/*.sql under a Postgres advisory lock, so concurrently booting replicas don’t race the schema. Applied versions are recorded in schema_migrations.

  3. graphstore.OpendriverNeo4j

    Connect the graph driver and register a readiness probe.

  4. github.NewApp authingest.New(app, graph, log)

    Build the GitHub App client (it satisfies RepoSource) and inject it — plus the graph store and logger — into the indexer.

  5. worker.Newpoolserver.New

    The pool takes the queue + indexer; the server takes the session store, the queue, the pool as a Waker, and the App. Two goroutines start: pool.Run(ctx) and ListenAndServe.

  6. SIGTERMdraingraceful shutdown

    On signal: stop accepting HTTP, let in-flight requests finish, then let workers finish in-flight jobs (bounded). Anything still running is left running and recovered by the reaper next boot.

02

Connect — the OAuth handshake

Before any indexing, a user connects their GitHub App installation. This mints the session cookie every later request is authorized against.

  1. BrowserGET /api/connectServer

    Server mints a random CSRF state, signs it into a short-lived cookie, and redirects to GitHub’s authorize URL.

  2. GitHubredirect /github/callback?code&stateServer

    After the user approves, GitHub redirects back with an authorization code and the echoed state.

  3. ServervalidStateServer

    The returned state must match the signed cookie, or the request is rejected — CSRF defense.

  4. ServerExchangeCode · User · InstallationsGitHub

    Trade the code for a user token, read the login/ID, and list the user’s installations to pick the installation ID.

  5. ServerUpsertUser · CreateSessionPostgres

    Persist the user and a new opaque, high-entropy session token, then set it as an HttpOnly cookie. Because the token is unguessable, the DB lookup alone authorizes later requests — no signing needed.

From here on, every /api/* call carries the session cookie; s.session(r) looks it up in Postgres and yields the UserID + InstallationID the handler needs.
03

Full index — the user-initiated path

The headline flow. Notice the split: the server’s job ends the instant the row is durable (pending); all the real work happens later, on a worker. This is what makes it crash-safe and scalable.

Phase A · Enqueue (synchronous, milliseconds)

  1. BrowserPOST /api/index {repo}Server

    Authenticated by the session cookie. The body must be exactly {"repo":"owner/repo"}.

  2. ServerCountActiveIndexJobsPostgres

    Rate limit. If the user already has ≥ 3 index jobs pending or running, respond 429. One user can’t queue unbounded expensive work.

  3. ServerEnqueueJob(full_index)Postgres

    Insert a pending row with a caller-supplied id, kind full_index, the repo, installation, and user. This is the commit point — the work now survives a restart.

  4. Serverwaker.Wake()Pool

    A non-blocking nudge so an idle worker picks the job up now instead of waiting for its 2s poll. Purely latency; cross-replica work is still found by the poll.

  5. Server202 {jobId}Browser

    Accepted. The browser now polls GET /api/graph/{jobId}. The HTTP request is done; it never touched Neo4j.

Phase B · Execute (asynchronous, on a worker)

  1. WorkerClaimJob · FOR UPDATE SKIP LOCKEDPostgres

    The worker atomically flips the oldest eligible row to running. Full mechanics in §05.

  2. WorkerFullIndex(installation, repo)Indexer

    The worker decodes the kind and calls into the domain core with a fresh, timeout-bounded context (30 min default).

  3. IndexerDownloadRepo → tarballRepoSource

    Fetch the whole repo as a tarball into a temp dir (cleaned up on return). This is the only path that downloads the full repo.

  4. Indexerfilewalk.ReadRepocore.Graph

    Walk source files (skipping deps/build/minified), tree-sitter parse each, extract symbols & intra-file edges, and resolve imports against the file manifest — one in-memory graph.

  5. IndexerSaveGraph(repo, headSHA, g)GraphStore

    Replace the repo’s entire subgraph in Neo4j and record head_sha (looked up via HeadSHA if the push didn’t supply it).

  6. Workerg.ToJSON → CompleteJob(graph)Postgres

    Serialize the graph, store it on the row, and mark it done. For a full index the result graph is kept so the browser can render it.

  7. BrowserGET /api/graph/{id} → done{graph}Postgres

    The poll (scoped to the owning user) sees pending until the worker finishes, then done with the graph, or a generic failed. The dashboard draws it.

Why the split earns its keep: if the process dies between Phase A and the end of Phase B, the job is already durable and simply gets re-run. The browser’s slow, expensive work is decoupled from its fast HTTP request, and any replica can execute it.
04

Incremental update — the webhook path

Once a repo is indexed, GitHub push webhooks keep it live. The cost is proportional to the change, not the repo size — the tarball is never re-downloaded.

Phase A · Enqueue from the webhook

  1. GitHubPOST /webhook (push)Server

    Body read under a 25 MiB cap, then the HMAC-SHA256 signature is verified against the shared secret. A bad signature is 401, full stop.

  2. ServerfilterServer

    Drop irrelevant events without error (so GitHub won’t retry): non-default-branch pushes, or missing repo/installation. A push’s complete flag is set false when it carries ≥ 20 commits (GitHub truncates the file lists).

  3. ServerEnqueueJob(push, {before,after,changed,complete})Postgres

    The changed-file union across commits is marshaled into the job payload. Same durable-insert commit point as a full index.

  4. Server204 · Wake()GitHub

    Fast ack. Crucially: if the enqueue itself fails, the server returns a non-2xx so GitHub retries — the push is never silently lost.

Phase B · ProcessPush decides: surgical or fallback

  1. WorkerProcessPush(before, after, changed, complete)Indexer

    Claimed exactly like any job. The indexer first reads the stored head from the graph store.

  2. IndexerGetHead == before ?Indexer

    The gate that chooses the path 👇.

Fallback → full re-index when head == "" (never indexed), head != before (drift — we missed a push), or !complete (truncated payload). It calls the same FullIndex from §03 and stops. Robust by construction.
Otherwise → surgical incremental. Continue:
  1. IndexerGetFileContent(path, after) — per changed fileRepoSource

    Fetch only the changed files at the new SHA — one API call each, not the whole repo.

  2. IndexerParseFile → ReplaceFile / DeleteFileGraphStore

    Exists → parse and swap that one file’s subgraph. Gone (or unparseable/too big) → delete it. Adds/removes flip a structural flag because the manifest changed.

  3. IndexerrecomputeImports by blast radiusGraphStore

    Modify-only → re-resolve just the changed files’ outbound imports (SetImports). Structural → RebuildImports, since inbound edges can shift when the file set changes.

  4. IndexerSetHead(after) → CompleteJobGraphStore

    Advance the stored head and mark the job done (no result graph for pushes).

05

The heart — FOR UPDATE SKIP LOCKED

This one query is what lets any number of workers, across any number of replicas, drain the same table without stepping on each other — and guarantees a single repo is never processed twice at once.

-- ClaimJob: flip the oldest eligible pending row to 'running', atomically.
UPDATE jobs SET status = 'running', started_at = now(), attempts = attempts + 1
WHERE id = (
    SELECT j.id FROM jobs j
    WHERE j.status = 'pending'
      -- serialize per repo: skip a repo that already has a running job (any kind)
      AND NOT EXISTS (
          SELECT 1 FROM jobs r WHERE r.repo = j.repo AND r.status = 'running'
      )
    ORDER BY j.created_at
    FOR UPDATE SKIP LOCKED   -- ← other workers skip this locked row, grab the next
    LIMIT 1
)
RETURNING ...;
SKIP LOCKED
Two workers running this at once never block each other and never claim the same row: the first locks it, the second’s SELECT simply steps over the locked row to the next candidate. No global lock, no polling contention.
NOT EXISTS (running)
The per-repo serializer. A repo with a job already running is invisible to the claim — so repo A and repo B run in parallel, but two jobs for repo A never do. Kind-agnostic: a push waits behind a full index of the same repo.
Partial unique index
jobs_one_running_per_repo enforces the invariant at the storage layer even under a race: if two workers slip past the NOT EXISTS check simultaneously, one UPDATE wins and the other hits a unique violation, which ClaimJob catches and treats as “not claimed,” retrying the next candidate.
ORDER BY created_at
Roughly FIFO fairness across the eligible set, so old work isn’t starved by newer arrivals.
Belt and suspenders. The NOT EXISTS filter avoids the collision in the common case; the unique index is the hard guarantee that survives the race the filter can’t see. Together they give at-most-one-running-per-repo across the whole fleet — which is also why the in-process lock that used to live in ingest was redundant and got removed.
06

A job’s whole life

Four states, three background forces. The maintenance loop (running every 10 min, and once promptly on boot) is what closes the crash-safety story.

pending — claimable running — held by a worker done — terminal, success failed — terminal, exhausted maintenance-loop transitions
Reaper safety margin: ReapAfter (45 min default) deliberately exceeds JobTimeout (30 min), so a job that is legitimately still running is never mistaken for a dead one. Only a job whose worker actually vanished stays running long enough to be reaped back to pending.
07

What happens when things go wrong

The failure paths are where the design pays off. Each row is a real case the code handles.

SituationWhat the system doesEnds as
Worker dies mid-job Row stays running. The maintenance loop’s ReapStuckJobs finds it after ReapAfter and returns it to the queue. Live work is never reaped because the threshold exceeds the job timeout. reaped → pending
Job errors (transient) FailJob checks attempts. Below max_attempts it goes back to pending for retry — which also frees the per-repo running slot. pending
Job errors repeatedly Once attempts hit max_attempts, it’s marked terminal. The browser sees a generic “indexing failed” — internal detail stays in the logs. failed
Webhook enqueue fails Server returns a non-2xx so GitHub retries the delivery. The push is not acked until it’s durably queued. retried by GitHub
Two workers race one repo The NOT EXISTS filter usually prevents it; if both slip through, the partial unique index rejects the loser with a unique violation, caught and retried as “not claimed.” one running
Missed a push (drift) ProcessPush sees stored head != before and falls back to a full re-index — self-healing without operator action. full re-index
Push with ≥ 20 commits GitHub truncates the changed-file lists, so complete=false → full re-index rather than a partial, wrong update. full re-index
User floods index requests The 4th concurrent full-index job is rejected with 429 until one drains. 429
Graceful shutdown HTTP drains first, then in-flight jobs finish within the grace window. Anything past it is left running and reaped on the next boot. resumed next boot
Terminal jobs pile up DeleteFinishedJobs evicts done/failed rows older than the retention TTL, bounding table and stored-graph growth. evicted

The one-line version: the server only ever enqueues into a durable Postgres queue and polls it; a horizontally-scalable worker pool drains it through ingest, which talks to the world exclusively through the RepoSource and GraphStore interfaces it declares — full downloads for first/fallback indexes, single-file fetches for surgical pushes — landing every change in Neo4j.
